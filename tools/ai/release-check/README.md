# Independent release-agreement check for apsw

Before an apsw release, independently verify that **apsw completely agrees with the SQLite release it
is built against** — every constant, every API, every enumerated code, the session surface, and the
*semantics* that changed between the old SQLite and the new one. This directory is written for a
*fresh agent* six months from now: enough to understand *what agreement means* and *how to check it
independently*, deliberately **not** a rigid runbook. The exact constants, APIs, version numbers, and
the contents of SQLite's release notes all change every release — so this describes the *method* and
leaves the specifics to be re-derived against whatever SQLite is current then.

## What the maintainer already does (so this complements, not repeats)

apsw already has a thorough, mostly *generative* agreement pipeline, driven from SQLite's shipped
table-of-contents database `toc.db` (which lists SQLite's APIs and constants — **except the session
extension**, which SQLite omits from it). The maintainer hand-maintains `tools/tocupdate.sql` to fill
that gap (the whole session/changegroup/rebaser surface, some FTS5 constants) and to patch SQLite's
own quirks (e.g. delete a duplicated or useless constant, re-add one a new SQLite removed but apsw
must keep for back-compat, mark the rebaser APIs non-experimental). From that, `tools/genconstants.py`
generates the exposed constants, `tools/code2rst.py` generates the docs, `make unwrapped`
(`tools/gensqlitedebug.py`) finds SQLite APIs apsw does not wrap, `make stubtest` checks the type
stubs, and `make showsymbols` checks no stray public C symbols leak. That pipeline is excellent — and
it is *generated from files the maintainer controls*, so its one blind spot is **staleness in those
very files against a new SQLite**: a `tocupdate.sql` entry that a release made wrong, a hand-patch
that a release made unnecessary or harmful, a session API added upstream that the hand-maintained
list missed.

This check exists to catch exactly that blind spot, by being **independent**: derive ground truth
from SQLite's own authoritative artifacts, and diff against what apsw *actually exposes at runtime* —
never against apsw's own generators. If the independent check and the generated pipeline agree, that
is strong confirmation; where they disagree is a release bug found before ship.

## The three rules that make it independent

1. **Ground truth comes from SQLite, not from apsw.** The authoritative sources are the ones SQLite
   ships: the amalgamation header `sqlite3.h` (the `#define`s are ground truth for constant *values*;
   the `SQLITE_API` declarations for the *function* set), the session surface compiled into
   `sqlite3.c` under its enable guard, `toc.db`, the SQLite documentation, and the **release
   changelog**. Read those — do not read `tools/tocupdate.sql` or `src/constants.c` and call it
   agreement, because that only checks apsw against itself.
2. **Diff against what apsw exposes at *runtime*.** `import apsw` and enumerate the real thing: the
   top-level `SQLITE_*` / `FTS5_*` constants, the `mapping_*` dictionaries (apsw's name↔value maps),
   `apsw.compile_options`, and the wrapped methods/classes. A bug in `genconstants.py` or a stale
   `tocupdate.sql` shows up here and would be invisible if you compared source-to-source.
3. **Cross-check SQLite's own sources against each other.** The header, `toc.db`, and the docs are
   generated by different parts of SQLite's build and can disagree — `toc.db` can lag a late header
   change; a doc page can describe an intent the constant value contradicts. A disagreement *among*
   them is itself a finding (and often explains a hand-patch in `tocupdate.sql`). Treat the header as
   truth for values, `toc.db`/docs for intent and grouping.

## Three outcomes (same discipline as the rest of `tools/ai`)

- **A real apsw gap** — a constant missing or with the wrong value, a `mapping_*` that is incomplete
  or not bidirectional, a newly added SQLite API that should be wrapped and is not, a session entry
  the hand-maintained list missed, a changed default apsw still assumes the old value of.
- **A deliberate, documented omission** — apsw chooses not to wrap something (a reason exists in the
  code/docs or the unwrapped allowlist). Confirm the reason *still holds* against the new release;
  re-validate it, do not rubber-stamp it.
- **A SQLite-side quirk apsw already compensates for** — a `toc.db`-vs-header disagreement that is
  SQLite's, which a `tocupdate.sql` patch already handles. Confirm the compensation is still correct
  for the new version (the re-added or deleted constant may have changed status upstream).

## Positive control

Prove the check can fail before trusting a clean run: against the *previous* SQLite release, plant a
known delta — a constant the new version added, removed, or renumbered — and confirm the method
flags it as missing/changed. A check that stays green on a planted delta is not reading the right
ground truth; fix it before believing this release is in agreement.

## The files

- `constants-and-apis.md` — the symbol-level diff: constants (presence **and** value **and**
  bidirectional `mapping_*`), the enumerated code families, and functions (wrapped / deliberately
  unwrapped), each derived from the current `sqlite3.h` and diffed against runtime apsw.
- `session-and-exceptions.md` — the hand-maintained surfaces where drift hides: the session extension
  (omitted from `toc.db`), FTS5, and each `tocupdate.sql` quirk-patch — how to re-derive them from
  SQLite directly and re-validate every hand-patch against the new release.
- `changelog-and-semantics.md` — the diff a symbol comparison cannot see: read SQLite's release notes
  between the two versions and check each new/changed/removed/deprecated item for the apsw response it
  needs (a new constant, a wrapped API, a changed default, a behaviour apsw documents or tests).

The reusable move: pick a category SQLite defines (a constant family, the function set, the session
surface, a changelog entry), derive its ground truth from SQLite's own artifacts, diff it against
what `import apsw` actually exposes, and classify each difference into the three outcomes. Then take
the next category.
